## 인증(Authentication)

- 정의 : 컴퓨터 시스템, 네트워크 또는 데이터에 액세스하려는 사용자, 기기, 애플리케이션의 신원을 검증하여 안전성을 보장하는 프로세스(Authentication)입니다.
- 시스템에 접근하려는 사용자가 주장하는 신원(ID)이 실제 본인이 맞는지를 확인하는 프로세스
- 인증과 인가의 차이
	- 인증은 사용자가 '누구인지' 확인하는 신원 증명 과정
	- 인가는 인증된 사용자가 '무엇을 할 수 있는지' 권한을 허가하는 과정
	- 인증이 먼저 발생하여 사용자 정체성을 확보한 후, 인가 단계에서 접근 권한을 결정한다.

### 인증 요소

1. 지식 기반 인증 : 사용자가 알고 있는 정보
	- 예 : Password, PIN, 보안 질문
2. 소유 기반 인증 : 사용자가 소유한 기기 / 물건
	- OTP, SMS 인증번호, 스마트 카드, 보안 토큰
3. 생체 기반 인증 : 신체적 특징
	- 지문, 홍채, 얼굴 인식, 목소리
4. 행위 기반 인증 : 사용자의 고유 행동 패턴
	- 서명, 걸음 걸이


### 인증 방식

1. SFA(Single-Factor-Authentication) : 단일 요소 인증
	- ID / PW 하나만 사용하는 방식
2. 2FA(Two-Factor-Authentication) : 2가지 서로 다른 인증 요소를 결합
	- 비밀번호 + OTP, 비밀번호 PIN 등 2가지의 인증 방식을 사용
3. MFA(Multi-Factor-Authentication) : 2개 이상의 서로 다은 요소를 조합
	- 비밀번호 + OTP + 지문 인증 등 2가지 이상의 인증 요소를 사용하는 경우
	- 일반적으로는 2FA도 MFA 포함시키지만 좁은 의미로는 3개 이상을 의미할때 사용

### 주요 인증 수단 및 기술

1. ID/PW 로그인
	- 사용자가 ID와 PW를 입력하여 본인임을 증명하는 가장 기본적인 인증 방식
	- 서버는 입력된 ID/PW를 DB에 저장된 계정 정보와 비교하여 인증 성공 여부를 판단
	- 안전을 위해 비밀번호는 평문으로 저장하지 않고, 보통 Hash 처리된 값과 비교
	- 인증에 성공하면 이후 요청을 식별하기 위해 세션 또는 토큰을 발급하는 과정으로 이동
2. 세션 기반 인증
	- 사용자가 로그인에 성공하면 서버가 세션(Session)을 생성하고, 클라이언트에는 세션 ID를 쿠키로 전달하는 방식
	- 사용자가 요청을 보낼 때 브라우저는 쿠키에 저장된 세션 ID를 함께 전송
	- 서버는 전달받은 세션 ID를 이용해 서버에 저장된 세션 정보를 조회하고, 사용자가 인증된 상태인지 확인
	- 세션 정보가 서버에 저장되기 때문에 서버 측에서 강제 로그아웃, 세션 만료, 권한 변경 등을 관리하기 쉬움
	- 단점으로는 사용자가 많아질수록 서버의 세션 저장소 관리 부담이 증가
3. 토큰 기반 인증
	- 사용자가 로그인에 성공하면 서버가 Access Token 같은 인증 토큰을 발급하고, 클라이언트가 이후 요청에 해당 토큰을 포함하여 보내는 방식
	- 보통 API 요청 시 `Authorization: Bearer <token>` 형태로 헤더에 포함
	- 서버는 전달받은 토큰을 검증하여 사용자의 인증 상태와 권한 정보를 확인
	- JWT 같은 토큰은 토큰 자체에 사용자 식별 정보, 만료 시간, 권한 정보 등을 포함할 수 있음.
	- 서버가 세션을 직접 저장하지 않아도 되는 구조로 만들 수 있어 API 서버, 모바일 앱, SPA 환경에서 자주 사용
	- 단, 토큰이 탈취되면 만료 전까지 악용될 수 있으므로 짧은 만료 시간, Refresh Token, HTTPS 사용, 안전한 저장 방식이 중요
4. API Key 인증
	- API 요청 시 고유한 키를 헤더나 쿼리 파라미터 등에 포함하여 요청 주체를 식별하는 방식
	- 예를 들어 `X-API-Key: <api_key>` 같은 형태로 요청에 포함할 수 있음.
	- 주로 외부 서비스 연동, 서버 간 통신, 개발자용 API 호출에서 사용
	- API Key는 “어떤 사용자 개인이 로그인했는지”보다는 “어떤 애플리케이션 또는 클라이언트가 요청했는지”를 식별하는 성격
	- 단독으로 강한 사용자 인증 수단으로 사용하기보다는 요청 제한, 서비스 식별, 접근 제어와 함께 사용하는 경우가 많음.
	- 키가 노출되면 누구나 해당 권한으로 API를 호출할 수 있으므로, 키 보관, 주기적 교체, 권한 범위 제한, IP 제한 등이 필요
5. SSO (Single Sign-On)
	- 한 번의 로그인으로 여러 서비스나 시스템에 접근할 수 있도록 하는 인증 방식
	- 사용자는 중앙 인증 서버 또는 외부 인증 제공자에서 로그인하고, 각 서비스는 해당 인증 결과를 신뢰하여 접근을 허용
	- 예를 들어 Google 계정으로 여러 서비스에 로그인하거나, 회사 계정으로 사내 여러 시스템에 접근하는 방식이 SSO에 해당
	- SAML, OAuth 2.0, OpenID Connect 같은 표준 프로토콜이 자주 사용
	- 사용자는 여러 서비스마다 ID/PW를 따로 입력하지 않아도 되어 편리하고, 조직 입장에서는 계정 관리와 접근 제어를 중앙에서 관리하기 쉬움
	- 단, 중앙 인증 계정이 탈취되면 연결된 여러 서비스에 영향을 줄 수 있으므로 MFA, 세션 관리, 접근 로그 모니터링이 중요
6. 공동인증서
	- 공동인증서는 사용자의 신원을 전자적으로 증명하기 위해 사용하는 인증 수단
	- 과거에는 공인인증서라고 불렸으며, 현재는 공동인증서라는 명칭으로 사용
	- 사용자는 인증서 파일과 인증서 비밀번호를 이용하여 본인임을 증명
	- 주로 금융 서비스, 공공기관, 전자서명, 본인확인 등의 환경에서 사용
	- 공동인증서는 공개키 기반 구조(PKI, Public Key Infrastructure)를 사용
	- 인증서 저장 위치 관리, 비밀번호 관리, 악성코드 감염 방지, 안전한 기기 사용이 중요


### 주요 인증 표준 및 프로토콜

1. FIDO(Fast IDentity Online)
	- 비밀번호 의존도를 줄이고, 공개키 암호화 기반으로 안전한 인증을 제공하기 위한 국제 인증 표준 프레임워크
	- 사용자의 비밀번호를 서버에 직접 저장하거나 전송하지 않고, 사용자 기기 내 인증 장치와 공개키/개인키 쌍을 이용하여 인증
	- 지문, 얼굴 인식, PIN, 보안 키 등 다양한 인증 수단을 사용
	- 피싱 사이트에서는 정상 도메인과 매칭되는 인증 정보가 없기 때문에 피싱 공격에 강한 편
	- FIDO는 크게 기존 FIDO UAF/U2F 계열과, 최신 FIDO2 계열로 구분
	- 대표적인 예시로는 모바일 앱에서 지문이나 얼굴 인식을 통해 사용자를 확인하는 방식, 보안 키를 이용한 2단계 인증, 패스키를 이용한 웹 로그인 등이 있음
	1. UAF(Universal Authentication Framework)
		- 지문, 얼굴 인식 등 사용자의 생체 정보나 로컬 인증 수단을 이용해 비밀번호 없이 인증하는 방식
		- 사용자의 생체 정보 자체가 서버로 전송되는 것이 아니라, 기기 내부에서 사용자를 확인한 뒤 암호학적 인증 결과를 서버에 전달
		- 모바일 환경의 비밀번호 없는 인증에 자주 사용되는 개념
	2. U2F(Universal 2nd Factor) / CTAP1
		- ID/PW 로그인 이후 추가 인증 요소로 보안 키를 사용하는 2단계 인증 방식
		- 사용자는 먼저 ID/PW로 로그인하고, 이후 USB, NFC, BLE 등을 통해 연결된 FIDO 보안 키로 추가 인증을 수행
		- 비밀번호가 탈취되어도 물리적인 보안 키가 없으면 로그인이 어렵기 때문에 계정 탈취 방어에 효과적
		- 현재 FIDO2에서는 기존 U2F를 CTAP1이라는 이름으로 호환 지원
		- 예) 암호화폐 거래소 계정에서 ID/PW 로그인 후 YubiKey 같은 FIDO 보안 키를 터치하여 2차 인증을 수행하는 방식
		- 예) 암호화폐 거래소에서 출금, 보안 설정 변경 등 민감한 작업을 할 때 FIDO 보안 키 인증을 추가로 요구하는 방식
	3. FIDO2
		- WebAuthn과 CTAP를 기반으로 하는 최신 FIDO 표준
		- 웹 브라우저, 운영체제, 보안 키, 생체 인증 장치 등을 이용해 비밀번호 없는 인증 또는 강한 2단계 인증을 구현할 수 있음
		- 대표적으로 패스키(passkey), WebAuthn 기반 웹 로그인, 보안 키 로그인, 생체 인증 기반 웹 로그인 등에 사용
		- 사용자는 웹사이트나 앱에서 비밀번호 대신 지문, 얼굴 인식, PIN, 보안 키 등을 이용해 로그인할 수 있음
		- 이때 지문이나 얼굴 정보 자체가 웹사이트 서버로 전송되는 것이 아니라, 기기 내부에서 사용자를 확인한 뒤 공개키 암호화 기반의 인증 결과만 서버에 전달됨
		- 예) Google 계정에서 패스키를 등록한 뒤 스마트폰 지문이나 화면 잠금으로 로그인하는 방식
		- 예) 웹사이트에서 “패스키로 로그인”, “보안 키로 로그인”, “지문으로 로그인” 같은 기능을 제공하는 경우
2. WebAuthn(Web Authentication)
	- 웹 서비스에서 FIDO 인증을 사용할 수 있도록 만든 W3C 표준 웹 API
	- 웹 브라우저와 웹 애플리케이션이 사용자의 인증 장치와 상호작용하여 공개키 기반 인증을 수행
	- 서버는 사용자의 공개키를 저장하고, 사용자의 개인키는 사용자의 기기 또는 보안 키 내부에 안전하게 보관
	- 로그인 시 서버가 Challenge 값을 보내면, 사용자의 인증 장치가 개인키로 서명하고 서버는 저장된 공개키로 이를 검증
	- 비밀번호가 직접 전송되지 않기 때문에 비밀번호 재사용, 비밀번호 유출, 피싱 공격에 강한 구조
	- 패스키(passkey), 생체 인증 기반 로그인, 보안 키 로그인 등을 구현할 때 사용
	- WebAuthn은 단독 기술이라기보다 FIDO2를 웹 환경에서 사용할 수 있게 해주는 핵심 구성 요소로 보는것이 좋음.
3. Passkey
	- Passkey는 비밀번호 없이 로그인할 수 있도록 만든 FIDO2/WebAuthn 기반의 인증 방식
	- 사용자는 비밀번호 대신 지문, 얼굴 인식, PIN, 기기 잠금 해제 등의 방식으로 본인 확인을 수행
	- 서비스 서버에는 사용자의 공개키가 저장되고, 개인키는 사용자의 기기 또는 계정 동기화 저장소에 안전하게 보관
	- 로그인 시 서버는 Challenge 값을 보내고, 사용자의 기기는 개인키로 서명한 응답을 서버에 전달
	- 서버는 저장된 공개키로 서명을 검증하여 사용자가 정상적인 인증 정보를 가지고 있는지 확인
	- 비밀번호를 입력하지 않기 때문에 비밀번호 재사용, 비밀번호 유출, 피싱 공격 위험을 줄일 수 있음
	- 사용자는 사이트마다 복잡한 비밀번호를 기억하지 않아도 되고, 생체 인증이나 기기 잠금 해제만으로 로그인 가능
	- 단, 기기 분실, 계정 복구, 동기화 계정 탈취 등에 대비한 복구 수단과 추가 보안 설정이 중요
4. OpenID Connect(OIDC)
	- OpenID Connect는 OAuth 2.0 위에 사용자 인증 기능을 추가한 인증 프로토콜
	- OAuth 2.0이 “권한 위임”을 위한 인가 프로토콜이라면, OpenID Connect는 “사용자가 누구인지 확인”하기 위한 인증 계층
	- 소셜 로그인에서 “Google로 로그인”, “Kakao로 로그인”, “Naver로 로그인” 같은 기능을 구현할 때 자주 사용
	- 로그인에 성공하면 Access Token과 함께 ID Token을 받을 수 있음
	- ID Token은 사용자의 식별자, 발급자, 대상 서비스, 만료 시간 등의 정보를 담고 있으며 보통 JWT 형식으로 전달됨
	- 서비스는 ID Token을 검증하여 사용자가 정상적으로 인증되었는지 확인
	- OAuth 2.0만 사용하면 “이 앱이 어떤 API에 접근할 수 있는가”를 다루고, OpenID Connect를 사용하면 “이 사용자가 누구인가”까지 확인할 수 있음
	- OIDC는 여러 서비스에서 하나의 계정으로 로그인하는 SSO 구조를 구현할 때 자주 사용


### 인증 관련 보안 개념

1. Hash
	- 임의의 데이터를 고정된 길이의 값으로 변환하는 단방향 처리 방식
	- 원본 데이터를 다시 복구할 수 없기 때문에 비밀번호 저장에 자주 사용
	- 로그인 시 입력한 비밀번호를 Hash 처리한 뒤, DB에 저장된 Hash 값과 비교하여 인증 여부를 판단
	- 대표적으로 SHA-256, bcrypt, scrypt, Argon2 등이 있음
	- 비밀번호 저장에는 단순 SHA 계열보다 bcrypt, scrypt, Argon2처럼 비밀번호 저장에 특화된 알고리즘을 사용하는 것이 좋다.
2. Salt
	- 비밀번호를 Hash 처리하기 전에 추가하는 임의의 랜덤 값
	- 같은 비밀번호라도 서로 다른 Salt를 사용하면 Hash 결과가 달라짐
	- 공격자가 미리 만들어둔 Rainbow Table을 이용해 비밀번호를 역추적하는 것을 어렵게 만듦
	- 보통 사용자마다 서로 다른 Salt를 생성하여 비밀번호 Hash와 함께 저장함
3. Encoding
	- 데이터를 특정 형식으로 변환하는 방식
	- 원본 데이터를 숨기기 위한 보안 기술이 아니라, 전송이나 저장을 위해 표현 방식을 바꾸는 것
	- Base64, URL Encoding, HTML Entity Encoding 등이 대표적
	- Encoding은 누구나 다시 원래 값으로 복원할 수 있으므로 암호화나 Hash와 구분해야 함
	- 예: 공백을 `%20`으로 표현하거나 '='을 '%3d'로 표현하거나, 바이너리 데이터를 Base64 문자열로 표현
4. Encryption
	- 데이터를 암호문으로 변환하여 권한 없는 사람이 내용을 읽지 못하게 하는 방식
	- Hash와 달리 복호화 키가 있으면 원본 데이터를 다시 복구할 수 있음
	- 개인정보, 토큰, 민감한 설정값 등을 보호할 때 사용
	- 대표적으로 AES 같은 대칭키 암호화와 RSA 같은 공개키 암호화가 있음
	- 중요한 점은 암호화 알고리즘뿐 아니라 \[키 관리]가 매우 중요하다는 것
5. Cookie
	- 웹 브라우저에 저장되는 작은 데이터 조각
	- 서버가 `Set-Cookie` 헤더로 쿠키를 저장하게 하고, 브라우저는 이후 요청마다 해당 쿠키를 함께 전송
	- 세션 ID, 로그인 상태, 사용자 설정 등을 저장할 때 사용
	- 인증에 사용하는 쿠키는 `HttpOnly`, `Secure`, `SameSite` 같은 보안 속성을 설정하는 것이 중요
	- 쿠키에 민감한 정보를 평문으로 직접 저장하는 것은 위험
6. Session
	- 서버가 사용자의 로그인 상태나 인증 정보를 관리하는 방식
	- 사용자가 로그인하면 서버는 세션을 생성하고, 클라이언트에는 세션 ID를 쿠키로 전달
	- 이후 요청에서 클라이언트가 세션 ID를 보내면 서버는 해당 세션 정보를 조회하여 사용자를 식별
	- 세션 정보는 서버 측에 저장되기 때문에 강제 로그아웃, 만료 처리, 권한 변경 관리가 쉬움
	- 단점으로는 사용자가 많아질수록 서버의 세션 저장소 관리 부담이 커질 수 있음
7. JWT
	- JSON Web Token의 약자로, JSON 형식의 정보를 안전하게 전달하기 위한 토큰 형식
	- 보통 Header, Payload, Signature 세 부분으로 구성
	- Payload에는 사용자 식별자, 권한, 만료 시간 같은 Claim 정보를 담을 수 있음
	- Signature를 통해 토큰이 위조되었는지 검증할 수 있음
	- 주로 토큰 기반 인증에서 `Authorization: Bearer <token>` 형태로 사용
	- 단, JWT Payload는 암호화된 것이 아니라 Base64URL로 인코딩된 것이므로 민감한 정보를 넣으면 취약함
	- 탈취된 JWT는 만료 전까지 악용될 수 있으므로 짧은 만료 시간, Refresh Token 관리, HTTPS 사용이 중요함


### 인증 취약점

1. Brute Force
	- 공격자가 가능한 비밀번호나 ID/PW 조합을 무차별적으로 반복 시도하여 계정에 접근하는 공격 방식
	- 비밀번호가 짧거나 단순할수록 공격 성공 가능성이 커짐
	- 대응 방법으로는 로그인 실패 횟수 제한, 계정 잠금, CAPTCHA, MFA, 강한 비밀번호 정책 등이 있음
2. Credential Stuffing
	- 다른 사이트에서 유출된 ID/PW 목록을 이용해 여러 서비스에 로그인을 시도하는 공격
	- 사용자가 여러 사이트에서 같은 비밀번호를 재사용할 때 위험성이 커짐
	- Brute Force와 달리 무작위 대입이 아니라 실제 유출된 계정 정보를 사용한다는 특징이 있음
	- 대응 방법으로는 MFA 적용, 비밀번호 재사용 방지 안내, 유출 계정 탐지, 비정상 로그인 탐지 등이 있음
3. Password Spraying
	- 여러 계정에 대해 `password123`, `qwer1234!` 같은 자주 쓰이는 비밀번호 하나 또는 소수의 비밀번호를 시도하는 공격
	- 특정 계정 하나에 많은 비밀번호를 넣는 Brute Force와 달리, 많은 계정에 같은 비밀번호를 넓게 뿌리는 방식
	- 계정 잠금 정책을 우회하기 위해 낮은 빈도로 시도되는 경우가 많음
	- 대응 방법으로는 약한 비밀번호 금지, 로그인 시도 패턴 탐지, MFA, IP/국가 기반 이상 징후 탐지 등이 있음
4. Session Hijacking
	- 사용자의 세션 ID를 탈취하여 공격자가 사용자인 것처럼 서비스에 접근하는 공격
	- 세션 쿠키 탈취, XSS, 네트워크 스니핑, 악성코드 등을 통해 발생할 수 있음
	- 세션 ID가 탈취되면 ID/PW를 몰라도 로그인된 사용자처럼 행동할 수 있음
	- 대응 방법으로는 HTTPS 적용, 쿠키 `HttpOnly`, `Secure`, `SameSite` 설정, 세션 만료 시간 설정, 로그인 후 세션 ID 재발급 등이 있음
5. 인증 우회
	- 정상적인 인증 절차를 거치지 않고 인증된 사용자처럼 접근하는 취약점
	- 예를 들어 로그인 여부 검증이 없는 관리자 페이지 접근, 클라이언트 측 검증만 믿는 로직, URL 직접 접근, 파라미터 조작 등이 해당
	- 인증 우회는 구현 실수나 서버 측 검증 부족에서 자주 발생
	- 대응 방법으로는 모든 보호 자원에 대해 서버 측 인증 검증을 수행하고, 인증과 인가 로직을 명확히 분리하는 것이 중요
6. JWT 취약점
	- JWT를 잘못 구현하거나 검증하지 않아 발생하는 인증 취약점
	- 예를 들어 서명 검증 누락, 약한 Secret Key 사용, 만료 시간 미설정, Payload에 민감정보 저장 등이 있음
	- JWT의 Payload는 암호화가 아니라 Base64URL 인코딩이므로 누구나 내용을 확인할 수 있음
	- 탈취된 JWT는 만료 전까지 악용될 수 있으므로 짧은 만료 시간, Refresh Token 관리, HTTPS, 안전한 저장 방식이 필요
	- 서버는 토큰의 서명, 만료 시간, 발급자, 대상자 등을 반드시 검증해야 함
7. MFA 우회
	- 다중 인증이 적용되어 있어도 이를 우회하거나 무력화하는 공격
	- 예를 들어 피싱 페이지를 이용한 OTP 탈취, 푸시 알림 반복 전송을 통한 승인 유도, 복구 코드 탈취, MFA 미적용 경로 악용 등이 있음
	- MFA가 있다고 해서 모든 공격이 차단되는 것은 아니며, 구현 방식과 사용자 보호가 중요
	- 대응 방법으로는 피싱에 강한 FIDO/WebAuthn 기반 인증, 로그인 알림, 의심스러운 위치 차단, 복구 절차 보호, MFA 재등록 절차 검증 등이 있음


### 안전한 인증 구현 방법

1. 비밀번호 평문 저장 금지
	- 사용자의 비밀번호를 DB에 그대로 저장하면 안 됨
	- DB가 유출될 경우 모든 사용자의 비밀번호가 그대로 노출될 수 있음
	- 비밀번호는 반드시 Hash 처리하여 저장해야 하며, 관리자도 원본 비밀번호를 알 수 없어야 함
2. 비밀번호 Hash + Salt 적용
	- 비밀번호는 단순 저장이 아니라 안전한 Hash 알고리즘을 사용해 저장해야 함
	- Salt는 비밀번호를 Hash 처리하기 전에 추가하는 랜덤 값
	- 같은 비밀번호라도 사용자마다 다른 Salt를 사용하면 서로 다른 Hash 값이 생성됨
	- Rainbow Table 공격이나 동일 비밀번호 사용자 식별을 어렵게 만들 수 있음
	- 비밀번호 저장에는 SHA-256 같은 빠른 Hash보다 bcrypt, scrypt, Argon2 같은 비밀번호 저장용 Hash 알고리즘을 사용하는 것이 좋음
3. 로그인 실패 횟수 제한
	- 공격자가 무차별적으로 비밀번호를 대입하는 것을 막기 위해 로그인 실패 횟수를 제한해야 합니다.
	- 일정 횟수 이상 로그인에 실패하면 계정 잠금, 일시 차단, CAPTCHA, 추가 인증 등을 적용할 수 있음
	- 단, 계정 잠금 기능은 공격자가 특정 사용자의 계정을 고의로 잠그는 데 악용할 수 있으므로 주의가 필요함
	- IP, 계정, 디바이스, 시간대 등을 함께 고려하여 이상 로그인 시도를 탐지하는 것이 좋음
4. MFA 적용
	- MFA는 Multi-Factor Authentication의 약자로, 두 가지 이상의 인증 요소를 사용하는 방식
	- ID/PW가 탈취되더라도 추가 인증을 요구하여 계정 탈취 가능성을 줄일 수 있음
	- 예를 들어 OTP, 이메일 인증, SMS 인증, 인증 앱, FIDO 보안 키, 생체 인증 등을 사용할 수 있음
	- 가능하면 피싱에 강한 FIDO/WebAuthn 기반 인증을 사용하는 것이 좋음
	- MFA 등록, 해제, 복구 과정도 공격 대상이 될 수 있으므로 해당 절차도 안전하게 보호해야 함
5. 세션 쿠키 보안 속성 설정
	- 세션 ID가 저장되는 쿠키에는 보안 속성을 설정해야 함
	- \`HttpOnly\`를 설정하면 JavaScript에서 쿠키에 접근하지 못하게 하여 XSS로 인한 쿠키 탈취 위험을 줄일 수 있음
	- \`Secure\`를 설정하면 HTTPS 통신에서만 쿠키가 전송되도록 제한할 수 있음
	- \`SameSite\`를 설정하면 CSRF 공격 위험을 줄이는 데 도움이 됨
	- 로그인 이후 세션 ID를 새로 발급하여 Session Fixation 공격을 방지하는 것도 중요함
6. JWT 만료 시간 설정
	- JWT는 탈취될 경우 만료 전까지 악용될 수 있으므로 만료 시간을 반드시 설정해야 함
	- Access Token은 짧은 만료 시간을 적용하고, 필요한 경우 Refresh Token으로 재발급하는 구조를 사용할 수 있음
	- JWT Payload에는 민감한 정보를 저장하면 안 됨
	- 서버는 JWT의 서명, 만료 시간, 발급자, 대상자 등을 반드시 검증해야 함
	- Refresh Token은 장기간 사용될 수 있으므로 안전한 저장, 회전, 재사용 탐지 정책이 필요함
7. 인증 실패 메시지 모호화
	- 로그인 실패 시 어떤 정보가 틀렸는지 구체적으로 알려주지 않는 것이 좋음
	- 예를 들어 “존재하지 않는 ID입니다”, “비밀번호가 틀렸습니다”처럼 구분해서 알려주면 계정 존재 여부를 추측할 수 있음
	- 대신 “ID 또는 비밀번호가 올바르지 않습니다”처럼 모호한 메시지를 사용하는 것이 무엇이 틀렸는지 확신할 수 없어서 안전함
	- 이를 통해 공격자가 유효한 계정을 수집하는 Account Enumeration 공격을 어렵게 만들 수 있음
8. 중요 기능 재인증 적용
	- 비밀번호 변경, 이메일 변경, 결제, 출금, MFA 해제, 계정 삭제 같은 중요 기능에는 재인증을 요구하는 것이 좋음
	- 사용자가 이미 로그인된 상태라도 세션 탈취나 자리 비움 상황을 고려해 추가 확인 절차가 필요함
	- 재인증 방식으로는 비밀번호 재입력, MFA 확인, 생체 인증, 이메일 확인 등을 사용할 수 있음
	- 특히 계정 보안 설정 변경이나 금전적 피해가 발생할 수 있는 기능에는 반드시 적용하는 것이 좋음
	- 예를 들어 \`비밀번호 재설정\`, \`인증방식 변경\` 등의 경우 재인증이 필요

## 인가(Authorization)

- 사용자, 시스템, 서비스 등이 특정 자원(데이터, 파일, 기능, API 등)에 접근하거나 작업을 수행할 권한이 있는지 확인하고, 허가 또는 거부하는 프로세스입니다.
- 인증(Authentication)이 “누구인지 확인하는 과정”이라면, 인가(Authorization)는 “무엇을 할 수 있는지 결정하는 과정”입니다.
- 인증에 성공한 사용자라도 권한이 없는 자원이나 기능에는 접근할 수 없도록 제한하는 핵심 보안 단계입니다.

### 인가의 기능

1. 접근 제어(Access Control)
	- 사용자가 인증(Authentication)을 마친 후 특정 데이터, API, 파일, 관리자 페이지 등에 접근할 수 있는지 권한을 확인합니다.
	- 예) 로그인한 사용자가 관리자 페이지에 접근하려 할 때 관리자 권한이 있는지 확인합니다.
2. 권한 허가/거부
	- 사용자 ID, 역할(Role), 권한(Permission), 세션, 토큰(JWT) 등을 기반으로 허용된 작업(읽기, 쓰기, 수정, 삭제 등)만 수행하도록 제한합니다.
	- 예) 일반 사용자는 게시글 조회만 가능하고, 작성자나 관리자는 수정/삭제가 가능하도록 제한합니다.
3. 보안 및 리소스 보호
	- 인증된 사용자라도 권한이 없는 중요 데이터나 기능에는 접근하지 못하게 하여 시스템 보안을 유지합니다.
	- 예) 관리자 권한은 주요 관리 페이지에 접근할 수 있고, 일반 사용자 권한은 일반 기능만 사용할 수 있습니다.


### 인가의 기능

1. 접근 제어
	- 인증된 사용자가 특정 자원에 접근할 수 있는지 확인하는 기능
	- 예를 들어 일반 사용자는 자신의 게시글만 수정할 수 있고, 관리자는 전체 게시글을 관리할 수 있음
	- 페이지, API, 파일, 데이터베이스 레코드 등 보호해야 하는 자원에 대해 접근 가능 여부를 판단
	- 접근 제어가 제대로 적용되지 않으면 다른 사용자의 정보 조회, 관리자 기능 접근 같은 문제가 발생할 수 있음
2. 권한 허가/거부
	- 사용자의 역할, 권한, 소유권 등을 기준으로 특정 작업을 허용하거나 거부하는 기능
	- 예를 들어 읽기, 쓰기, 수정, 삭제, 승인, 결제 같은 작업별 권한을 확인
	- 같은 자원에 접근하더라도 사용자 권한에 따라 가능한 작업이 달라질 수 있음
	- 서버는 요청이 들어올 때마다 해당 사용자가 그 작업을 수행할 권한이 있는지 검증해야 함
3. 보안 및 리소스 보호
	- 민감한 데이터와 시스템 기능이 허가되지 않은 사용자에게 노출되지 않도록 보호하는 기능
	- 개인정보, 결제 정보, 관리자 기능, 내부 API, 중요 파일 등이 보호 대상이 될 수 있음
	- 인가 검증을 통해 데이터 유출, 권한 상승, 비정상적인 기능 사용을 방지할 수 있음
	- 인증된 사용자라도 필요한 권한이 없다면 중요 리소스에 접근하지 못하도록 제한해야 함


### 인가 방식

1. RBAC(Role-Based Access Control)
	- 역할(Role)을 기준으로 권한을 부여하는 접근 제어 방식
	- 사용자에게 직접 권한을 하나씩 부여하는 것이 아니라, 역할에 권한을 부여하고 사용자를 해당 역할에 배정
	- 예를 들어 \`일반 사용자\`, \`운영자\`, \`관리자\` 같은 역할을 만들고, 역할마다 가능한 기능을 다르게 설정
	- 관리자는 게시글 삭제, 사용자 관리가 가능하지만 일반 사용자는 자신의 게시글 작성/수정만 가능하도록 제한할 수 있음
	- 구조가 단순하고 관리하기 쉬워 많은 웹 서비스와 사내 시스템에서 사용됨
	- 단점으로는 역할이 많아지면 관리가 복잡해지는 Role Explosion 문제가 발생할 수 있음
2. Permission-Based Access Control
	- 개별 권한(Permission)을 기준으로 접근 가능 여부를 판단하는 방식
	- 예를 들어 \`post:read\`, \`post:write\`, \`post:delete\`, \`user:manage\` 같은 세부 권한을 정의
	- 사용자가 특정 요청을 수행할 때 해당 권한을 가지고 있는지 확인하여 허가하거나 거부
	- RBAC보다 세밀한 권한 제어가 가능함
	- 실제 서비스에서는 RBAC와 함께 사용되는 경우가 많음
	- 예를 들어 \`관리자\` 역할에 \`post:delete\`, \`user:manage\` 권한을 묶어서 부여하는 방식
	- 권한이 세분화되어 있어 기능 단위의 접근 제어를 구현하기 좋지만, 권한 수가 많아지면 관리가 복잡해질 수 있음
3. 소유자 기반 접근 제어
	- 자원의 소유자 여부를 기준으로 접근을 허용하거나 거부하는 인가 방식
	- 예를 들어 사용자는 자신이 작성한 게시글만 수정하거나 삭제할 수 있음
	- 마이페이지, 주문 내역, 개인 게시글, 개인 파일, 댓글 수정 기능 등에서 자주 사용
	- 단순히 로그인 여부나 역할만 확인하는 것이 아니라, 요청한 사용자가 해당 자원의 소유자인지 서버 측에서 확인해야 함
	- 소유자 검증이 부족하면 다른 사용자의 게시글 수정, 주문 정보 조회, 개인정보 열람 같은 취약점이 발생할 수 있음
	- IDOR(Insecure Direct Object Reference) 취약점과 밀접하게 관련됨
4. ABAC
	- 사용자, 자원, 요청, 환경의 속성(Attribute)을 기준으로 접근 여부를 판단하는 방식
	- 예를 들어 사용자의 부서, 직급, 접속 위치, 시간, 자원의 등급, 요청 방식 등을 함께 고려
	- “인사팀 직원은 근무 시간에만 인사 문서에 접근 가능” 같은 조건 기반 정책을 만들 수 있음
	- RBAC보다 유연하고 세밀한 접근 제어가 가능함
	- 대규모 조직, 클라우드 환경, 민감한 데이터 접근 제어에서 사용하기 좋음
	- 단점으로는 정책 설계와 관리가 복잡해질 수 있음


### 주요 인가 표준 및 프로토콜

1. OAuth 2.0
	- 사용자의 ID/PW를 직접 공유하지 않고, 제3자 애플리케이션이 사용자의 자원에 제한적으로 접근할 수 있도록 권한을 위임하는 인가 프로토콜
	- 예를 들어 어떤 서비스가 사용자의 Google Drive 파일, GitHub 저장소, Kakao API의 사용자 정보 등에 접근하려고 할 때 사용됨
	- 사용자는 원본 서비스에 로그인한 뒤, 제3자 애플리케이션에 특정 권한을 허용할지 선택
	- 권한을 허용하면 Authorization Server가 Access Token을 발급하고, 제3자 애플리케이션은 이 토큰을 이용해 허용된 API에 접근
	- 일반적인 Authorization Code Flow에서는 Access Token을 바로 받기 전에 Authorization Code를 먼저 발급받고, 이를 Access Token으로 교환하는 과정을 거침
	- 사용자의 비밀번호를 제3자 애플리케이션에 직접 전달하지 않아도 된다는 장점이 있음
	- 접근 권한은 Scope를 통해 제한할 수 있음
	- 예를 들어 \`profile:read\`, \`email:read\`, \`repo:read\` 같은 범위만 허용할 수 있음
	- 사용자는 나중에 부여한 권한을 철회할 수 있음
	- OAuth 2.0만으로는 “사용자가 누구인지 인증”하는 목적에는 부족하며, 로그인 인증에는 OpenID Connect를 함께 사용함


### 인가 처리 위치

1. 클라이언트 검증과 서버 검증의 차이
	- 클라이언트 검증은 브라우저, 모바일 앱, 프론트엔드 코드에서 접근 가능 여부를 확인하는 방식
	- 예를 들어 권한이 없는 사용자에게 관리자 버튼을 숨기거나, 수정/삭제 버튼을 보이지 않게 처리하는 것이 해당
	- 사용자 경험을 개선하고 불필요한 요청을 줄이는 데 도움이 됨
	- 하지만 클라이언트 코드는 사용자가 직접 확인하거나 조작할 수 있으므로 보안 검증의 기준으로 삼으면 안 됨
	- 공격자는 개발자 도구, 프록시 도구, API 직접 호출 등을 통해 클라이언트 검증을 우회할 수 있음
	- 서버 검증은 요청을 받은 서버가 사용자의 권한, 역할, 소유권 등을 확인한 뒤 요청을 허용하거나 거부하는 방식
	- 실제 데이터 조회, 수정, 삭제, 관리자 기능 실행 여부는 반드시 서버 측에서 최종 판단해야 함
2. 서버 측 권한 검증의 중요성
	- 서버는 보호해야 할 자원에 접근하는 모든 요청에 대해 권한 검증을 수행해야 함
	- 사용자가 로그인되어 있더라도 해당 기능이나 데이터에 접근할 권한이 있는지는 별도로 확인해야 함
	- 예를 들어 게시글 수정 요청이 들어오면, 서버는 요청한 사용자가 해당 게시글의 작성자인지 또는 관리자 권한이 있는지 확인해야 함
	- 단순히 화면에서 버튼을 숨기는 것만으로는 보안이 되지 않음
	- URL 직접 접근, 파라미터 조작, API 직접 호출 등을 통해 권한 없는 요청이 서버로 전달될 수 있음
	- 서버 측 권한 검증이 부족하면 IDOR, 권한 상승, 관리자 기능 접근, 타 사용자 정보 조회 같은 취약점이 발생할 수 있음
	- 따라서 모든 중요 기능과 API에서는 인증 여부뿐 아니라 역할, 권한, 소유권까지 함께 검증해야 함


### 인가 취약점

1. IDOR(Insecure Direct Object Reference)
	- 사용자가 직접 접근 가능한 객체 ID 값을 조작하여 다른 사용자의 자원에 접근하는 취약점
	- 예를 들어 \`/orders/1001\` 요청을 \`/orders/1002\`로 바꿨을 때 다른 사용자의 주문 정보가 조회되는 경우
	- 서버가 요청 사용자의 권한이나 자원 소유자 여부를 제대로 확인하지 않아 발생
	- 단순히 URL, 파라미터, 파일명, 게시글 번호를 숨기는 것만으로는 방어할 수 없음
	- IDOR는 다른 사용자의 자원에 접근하는 수평적 권한 상승으로 이어지는 경우가 많음
	- 대응 방법으로는 서버 측에서 요청 사용자와 자원의 소유자 관계를 반드시 검증해야 함
2. 수평적 권한 상승
	- 같은 권한 수준의 다른 사용자 자원에 접근하거나 조작하는 취약점
	- 예를 들어 일반 사용자가 다른 일반 사용자의 개인정보, 주문 내역, 게시글, 파일 등에 접근하는 경우
	- 계정의 역할은 같지만, 접근 가능한 자원 범위가 서로 달라야 할 때 발생
	- IDOR와 함께 나타나는 경우가 많음
	- 대응 방법으로는 자원마다 소유자 검증을 수행하고, 사용자 ID를 클라이언트 입력값에만 의존하지 않아야 함
3. 수직적 권한 상승
	- 낮은 권한의 사용자가 높은 권한의 기능이나 자원에 접근하는 취약점
	- 예를 들어 일반 사용자가 관리자 페이지에 접근하거나, 관리자 API를 호출해 사용자 정보를 수정하는 경우
	- 단순히 관리자 메뉴를 화면에서 숨기는 것만으로는 방어할 수 없음
	- 서버 측에서 사용자 역할과 권한을 확인하지 않으면 URL 직접 접근이나 API 호출로 우회될 수 있음
	- 대응 방법으로는 모든 관리자 기능과 중요 API에서 역할과 권한을 서버 측에서 검증해야 함
4. 기능 수준 접근 제어 밓습
	- 특정 기능이나 API에 대해 권한 검증이 누락되어 권한 없는 사용자가 기능을 실행할 수 있는 취약점
	- 예를 들어 일반 사용자가 관리자 전용 사용자 삭제 API, 승인 API, 설정 변경 API를 호출할 수 있는 경우
	- 화면에서는 버튼이 보이지 않더라도 API 요청을 직접 보내면 기능이 실행될 수 있음
	- 기능 단위로 접근 권한을 검증하지 않고, 화면 제어에만 의존할 때 자주 발생
	- 대응 방법으로는 페이지, API, 기능 단위로 서버 측 권한 검증을 일관되게 적용해야 함
5. HTTP Method 변경 우회
	- 같은 URL이라도 HTTP Method에 따라 다른 기능이 수행되는 점을 악용해 권한 검증을 우회하는 취약점
	- 예를 들어 \`GET /users/1\`은 허용되지만, \`PUT /users/1\`이나 \`DELETE /users/1\` 요청에서 권한 검증이 누락된 경우
	- 또는 \`POST\` 요청은 검증하지만 \`PUT\`, \`PATCH\`, \`DELETE\` 요청은 제대로 검증하지 않아 우회되는 경우가 있음
	- 서버나 프레임워크 설정에 따라 \`_method=DELETE\`, \`X-HTTP-Method-Override\` 같은 방식으로 Method가 변경될 수도 있음
	- 항상 발생하는 취약점은 아니지만, 서버 라우팅이나 권한 검증이 Method별로 다를 때 문제가 될 수 있음
	- 대응 방법으로는 URL뿐 아니라 HTTP Method별로 권한을 검증하고, 허용하지 않는 Method는 명확히 차단해야 함


### 안전한 인가 구현 방법

1. 서버에서 권한 검증
	- 인가 검증은 반드시 서버 측에서 수행해야 함
	- 클라이언트에서 버튼을 숨기거나 페이지 접근을 막는 것은 사용자 편의용일 뿐, 보안 검증으로 볼 수 없음
	- 공격자는 개발자 도구, 프록시 도구, API 직접 호출 등을 통해 클라이언트 검증을 우회할 수 있음
	- 서버는 요청이 들어올 때마다 해당 사용자가 해당 기능이나 자원에 접근할 권한이 있는지 확인해야 함
2. 클라이언트 입력값 신뢰 금지
	- 클라이언트에서 전달되는 \`user_id\`, \`role\`, \`is_admin\`, \`price\`, \`owner_id\` 같은 값은 신뢰하면 안 됨
	- 공격자는 요청 파라미터, 쿠키, 헤더, JSON Body 등을 조작할 수 있음
	- 권한 판단에 필요한 정보는 클라이언트 입력값이 아니라 서버의 세션, 토큰, DB에 저장된 값을 기준으로 확인해야 함
	- 예를 들어 요청에 포함된 \`user_id\`를 그대로 믿지 말고, 로그인된 사용자 정보와 실제 자원의 소유자를 서버에서 비교해야 함
3. 세션/토큰 검증
	- 요청을 처리하기 전에 사용자의 세션이나 토큰이 유효한지 확인해야 함
	- 세션 기반 인증에서는 세션 ID가 유효한지, 만료되지 않았는지, 해당 사용자와 연결되어 있는지 확인
	- 토큰 기반 인증에서는 토큰의 서명, 만료 시간, 발급자, 대상자, 권한 범위 등을 검증
	- 인증이 확인된 뒤에도, 해당 사용자가 요청한 자원이나 기능에 접근할 권한이 있는지 별도로 확인해야 함
	- 즉, 인증 검증과 인가 검증을 구분해서 처리해야 함
4. 소유자 검증
	- 사용자가 특정 자원에 접근하거나 수정하려 할 때, 해당 자원의 소유자인지 확인해야 함
	- 예를 들어 게시글 수정, 주문 조회, 개인 파일 다운로드, 댓글 삭제 같은 기능에서 필요
	- 단순히 요청 URL이나 파라미터에 포함된 ID를 믿지 말고, DB에서 자원의 실제 소유자 정보를 조회한 뒤 로그인 사용자와 비교해야 함
	- 소유자 검증이 부족하면 IDOR나 수평적 권한 상승 취약점으로 이어질 수 있음
5. 관리자 권한 검증
	- 관리자 페이지나 관리자 API는 반드시 서버 측에서 관리자 권한을 검증해야 함
	- 프론트엔드에서 관리자 메뉴를 숨기는 것만으로는 충분하지 않음
	- 일반 사용자가 관리자 URL을 직접 입력하거나 API 요청을 직접 보내는 경우에도 서버가 차단해야 함
	- 사용자 관리, 권한 변경, 게시글 삭제, 시스템 설정 변경 같은 중요 기능은 역할과 권한을 모두 확인하는 것이 좋음
6. 401/403 구분
	- 인증되지 않은 사용자와 권한이 부족한 사용자의 응답을 구분하는 것이 좋음
	- \`401 Unauthorized\`는 로그인하지 않았거나 인증 정보가 유효하지 않은 경우에 사용
	- \`403 Forbidden\`은 인증은 되었지만 해당 자원이나 기능에 접근할 권한이 없는 경우에 사용
	- API 응답에서 401과 403을 구분하면 클라이언트 처리와 보안 로그 분석이 쉬워짐
	- 단, 응답 메시지는 너무 자세하게 작성하지 않아 불필요한 정보 노출을 줄이는 것이 좋음
	- 예를 들어 실제로는 401, 403, 404에 해당하는 상황이라도 사용자에게는 단순 에러 페이지를 보여주고, 서버 로그에는 실제 에러 유형과 요청 정보를 구분해서 남기도록 설정할 수 있음
	- 특히 관리자 페이지, 비공개 리소스, 타 사용자 자원 접근 시도처럼 리소스 존재 여부 자체가 힌트가 될 수 있는 경우에는 사용자에게 404 또는 일반 에러 페이지처럼 응답할 수 있음
7. 로그 기록
	- 인가 실패, 관리자 기능 접근, 권한 변경, 중요 자원 접근 같은 이벤트는 로그로 기록하는 것이 좋음
	- 로그에는 사용자 ID, 요청 IP, 요청 경로, HTTP Method, 시간, 성공/실패 여부 등을 남길 수 있음
	- 반복적인 인가 실패나 비정상적인 접근 시도를 탐지하는 데 도움이 됨
	- 단, 로그에 비밀번호, 토큰 원문, 개인정보 같은 민감정보를 그대로 저장하면 안 됨
	- 로그는 추후 사고 분석, 이상 행위 탐지, 감사 자료로 활용될 수 있음
